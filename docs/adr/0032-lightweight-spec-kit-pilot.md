# ADR-0032: Lightweight Spec Kit pilot

- **Status:** accepted
- **Date:** 2026-11-05
- **Deciders:** repository maintainer, implementation assistant

## Context

v0.007 spans multiple sessions and partially implemented capabilities. Chat history
and passing unit tests are insufficient to distinguish code completion from native
device acceptance. Existing AGENTS, standards, glossary, ADRs and protocol notes
already define the engineering policy and must remain canonical.

## Decision

Adopt GitHub Spec Kit v1.3.0 at commit 34a0d388eac671d656eb05b125ad3ed6056168ed,
with the first-party lean preset and reviewed project-local command/template overrides.
A local ctdo-lite registration preset makes all nine overrides render into native
skills; this avoids core auxiliary commands retaining their default prompt bodies.
Use capability-level spec/plan/tasks/verification artifacts and a linked release scope
map for the remaining v0.007 work. The current branch and working tree are preserved.
Codex skills are generated by the pinned CLI; other agents read the same Markdown.
The constitution indexes existing policy instead of duplicating it.

Separate implementation status, fixture evidence and device confirmation. Existing
user authorization carries across phases; templates add no automatic permission
gates. Record blockers without stopping unrelated authorized work. Ticket lifecycle
continues to follow the issue-tracker standard, not a second local label system.

No community extension, native event hook, automatic workflow, MCP server, CI or
application dependency is enabled. Bundled workflow/scripts remain inert unless
explicitly invoked; feature continuation uses explicit/default paths, not branch
creation. Tool upgrades are reviewed separately and staged before application.

## Consequences

More Markdown must be kept current, but task IDs and evidence survive agent/session
changes. The pilot does not retroactively certify earlier work or replace protocol
captures, benchmarks or Windows/iPhone acceptance. A source pin does not fully lock
transitive Python dependencies. Evaluate usefulness after one development cycle;
remove the development scaffold if upkeep exceeds its benefit, retaining useful specs.

## Alternatives considered

Full default workflow introduces redundant policy and repeated review gates. Keeping
only conversation history loses traceability. Both are less suitable for this pilot.
